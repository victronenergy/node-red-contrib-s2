## Context

`s2-resource` stores its identity in the `resourceId` property, rendered as a hidden input on the RM tab and generated by the editor (see the `unique-resource-id` change). The runtime sends it as `ResourceManagerDetails.resource_id` and, for `Transport: WebSocket`, substitutes it into the `s2-cem-config` URL.

The S2 JSON schema types IDs as `[a-zA-Z0-9\-_:]{2,64}` ("an identifier expressed as a UUID"). s2python overrides `ResourceManagerDetails.resource_id` with `uuid.UUID`, so a Python CEM rejects anything that isn't a UUID.

## Goals / Non-Goals

**Goals:**
- A WebSocket user can read and copy the ID, and replace it with one their CEM expects.
- Invalid or duplicate IDs are caught in the editor, before deploy.

**Non-Goals:**
- Showing or editing the ID for D-Bus or External transports.
- Changing `s2-rm-config`'s existing Resource ID field.
- Runtime validation of the configured ID beyond the existing duplicate refusal and outgoing schema validation.

## Decisions

### One property, moved input
The existing `resourceId` property stays the single source; its input moves from a hidden field on the RM tab into the WebSocket section of the Connection tab as a text field. Node-RED reads inputs of hidden sections on save, so a D-Bus or External node keeps saving its `resourceId` through the same input, invisible as before. No migration, no second "override" property to keep in sync. Switching transport neither clears nor regenerates it: the ID is the resource's identity, not a transport setting.

### Accept the S2 ID format, warn on non-UUID
The user chose to accept whatever the S2 schema allows, since the ID may be issued by a CEM, and warn without blocking when it isn't a UUID. The format check is anchored (`^...{2,64}$`): the schema's pattern is unanchored, so taken literally it accepts any string containing two valid characters, which is clearly not the intent. The UUID check accepts any UUID version, matching Python's `uuid.UUID`.

### Validate through the property's `validate`
A two-argument `validate` on `resourceId` returns a message string when invalid (supported since Node-RED 3.x, so in 4.1.0). That gives a red triangle and Node-RED's own deploy warning, the same treatment as every other invalid property. It checks both the format and duplicates among other `s2-resource`/`s2-rm-config` nodes, reusing `resourceIdNeedsReplacing`. An empty value is valid: older nodes may still have one, and showing them invalid on load would change existing flows; `oneditsave` fills an emptied field with a new ID.

The duplicate check runs for every transport. A deployed duplicate therefore also shows a red triangle in the editor, consistent with the runtime refusing it.

### Live warning in the dialog
The non-UUID warning updates as the user types, under the field, in a scoped `.s2-form` warning class like the existing `s2-ombc-advanced-warning`. Info hints in this dialog use `s2-resource-hint`; this is a caution about a value the user entered, so it uses the warning style.

## Risks / Trade-offs

- [User replaces an ID the CEM already knows] -> The CEM sees a new resource and loses its per-resource state. The tooltip says so; the field only appears for WebSocket, where the user typically has to match the CEM's registration anyway.
- [Validation now flags deployed duplicates in the editor] -> Intended; they are already refused at runtime and named in the log.
