## Context

`s2-rm`'s handshake/session/routing logic lives entirely inside its `registerType(RED)` callback (`src/nodes/s2-rm/index.ts`) - there's no way to construct that behavior except as a Node-RED node instance. `s2-ombc-config`'s friendly operation-mode editor is likewise a self-contained block of client-side jQuery inside `src/nodes/s2-ombc-config/index.html`. `s2-resource` needs both, embedded, without duplicating either. See `proposal.md` for why.

## Goals / Non-Goals

**Goals:**
- One extraction of `s2-rm`'s session logic that both `s2-rm` and `s2-resource` construct directly, with no behavior difference between them.
- One copy of the OMBC friendly-editor widget, loaded by both `s2-ombc-config` and `s2-resource`.
- `s2-resource`'s port layout stays deterministic and matches `s2-rm`'s exactly in the `External`/`None` configuration (see `s2-resource` spec's port-contract requirement).

**Non-Goals:**
- Redesigning `s2-rm`'s protocol behavior - this only changes where the code that implements it lives.
- A generic "N independent toggles each contributing ports" mechanism for future control types - this change only needs to solve it for two settings (Transport, Control type).

## Decisions

**Extract session logic into a plain class, not a shared mixin or base node type.** `s2-rm`'s `registerType` callback becomes a thin Node-RED wrapper around a new `S2ResourceManager` class (in `src/lib/s2/`, alongside the existing `session.ts`/`messages.ts`) that takes plain callbacks for "send to transport" and "emit to CEM-output" instead of calling `node.send()` directly. `s2-rm` and `s2-resource` each construct one and wire its callbacks to their own ports. Rejected: making `s2-resource` internally instantiate a hidden `s2-rm` Node-RED node - Node-RED nodes aren't designed to be constructed outside `registerType`, and it would leave a phantom node with no visible wires or status in the editor.

**Shared CEM connection stays a separate config node; RM identity does not.** `s2-resource`'s Connection tab picks an existing `s2-cem-config` node (same dropdown-plus-edit-pencil pattern every config-node reference in this codebase uses), because one CEM connection legitimately serves multiple resources. RM identity (`resourceId`, `roles`, ...) is folded directly into `s2-resource`'s own config instead of a separate `s2-rm-config` reference, because - checked against `s2-rm-config`'s actual fields - a resource ID and its roles are inherently 1:1 with one resource and were never actually shared in practice; the separate config node existed only because `s2-rm` needed one to be constructible as a node.

**Shared OMBC editor widget via a common client-side script, not duplication.** The friendly-editor functions (`addModeItem`, `defaultStandbyMode`, the friendly/advanced conversion, etc.) move into a script loaded once and referenced by both `s2-ombc-config/index.html` and `s2-resource/index.html` - Node-RED loads every enabled node's `.html` into one editor page, so functions defined by one node's script tag are callable from another's as long as load order is respected (`s2-resource` depends on the shared script, not the other way around, avoiding an order dependency). Rejected: duplicating the widget into `s2-resource` - the exact drift risk the "Abnormal only" and future OMBC editor changes are meant to avoid.

**`Transport: D-Bus` added during implementation, reusing `S2DbusTransport`.** Originally scoped out (depended on `2026-09-06-s2-dbus-transport` landing first, with no shared code to reuse yet). Once that change's D-Bus registration logic was itself extracted into a class (`S2DbusTransport`, `src/lib/transport/dbus.ts` - the same fix applied there: a shared class instead of node-only logic, so both `s2-dbus` and `s2-resource` construct it directly), adding it here became the same shape of work as `Transport: WebSocket` already is: construct the class, wire its events to the RM's callbacks instead of external ports. No new port-layout case - `D-Bus` is built-in exactly like `WebSocket` (`hasTransportOutput` is `transport === 'external'`, true for neither built-in option).

**OMBC control-type logic extracted the same way, discovered during implementation.** The proposal's "Control type: OMBC" behavior (system description push, instruction resolution, status confirmation, `StatusRequest`) is `s2-ombc`'s full server-side behavior, not just its config editor - the original design only covered extracting `s2-rm` and sharing the editor widget, leaving no non-duplicating way for `s2-resource` to get this. Fixed by applying the same pattern one more time: `s2-ombc`'s `registerType` body is extracted into `OMBCController` (`src/lib/s2/ombc-controller.ts`), callback-based like `S2ResourceManager`, with `s2-ombc` becoming a thin wrapper around it. `s2-resource` constructs both classes directly.

**Port layout, revised during implementation: input is always fixed at 1; only the output count varies.** The original "4 independent slots, each on or off" model didn't survive contact with `s2-rm`'s actual shape (a single input already multiplexes "from transport" and "from control-type node" commands - there's no separate transport-in/CEM-in split to begin with) or with `Control type: OMBC` needing somewhere to put its resolved `ModeInstruction`/`ModeRequest` events (the original model had no output for that case at all - see the OMBC-controller-extraction decision above, found the same way). The design that actually ships:
- **Input (always exactly 1)**, matching `s2-rm`'s own fixed single input. Dispatches by shape, not by which port it arrived on: a message carrying `payload.command` goes to the RM (`S2ResourceManager`) unconditionally; anything else goes to the built-in `OMBCController`, if one exists (`Control type: OMBC`) - and produces the same "must have a 'command' field" error `s2-rm` would if none exists.
- **Output "to transport"**, index 0, present only when `Transport: External`.
- **Output "downstream"**, always present, last index: raw "from CEM" messages (`s2-rm`'s port 2 shape) when `Control type: None`, or resolved OMBC instructions (`s2-ombc`'s port 1 shape) when `Control type: OMBC` - never both, so this is one slot whose *content* depends on `Control type`, not two slots toggled independently.

So the real range is 1 or 2 outputs (never 0 - "downstream" is unconditional) and a constant 1 input, not the "0, 2, or 4 ports" figure floated before implementation. `oneditsave` only ever recomputes `node.outputs` (from `Transport` alone); `node.inputs` never changes, which sidesteps needing `victron-virtual`'s dynamic-output-count pattern for inputs at all.

**`Transport: D-Bus` also gets the power-measurement relay, via a shared `PowerMeasurementCache` class.** Found from actual editor use: the original "no power-measurement relay, use `Transport: External` + `s2-dbus` if you need it" carve-out was a real gap, not a deliberate simplification worth keeping - the whole point of a built-in D-Bus transport is not needing a second node for the common case. `s2-dbus`'s cache-and-relay logic was extracted into `PowerMeasurementCache` (`src/lib/s2/power-measurement-cache.ts`), the same pattern as every other extraction in this change; `s2-dbus` itself was refactored to use it too, so there's one implementation instead of two. `s2-resource` constructs one only when `Transport: D-Bus`, feeding matched input values through it and looping `PowerMeasurement` commands back into `S2ResourceManager.handleInput` directly (same internal-loopback pattern `OMBCController`'s `onSendCommand` already uses) instead of an external port.

**Advertised Control Types follow the Control Type tab, not a separate checklist, when a control type is built in.** Found from actual editor use: showing both `s2-resource`'s Control Type tab (which control type is *implemented*) and the Resource Manager tab's Control Types checkboxes (which are *advertised* to the CEM) as independent choices read as duplicated, disconnected UI - a user picking `Control type: OMBC` shouldn't also have to remember to check "OMBC" in a different tab for the RM to actually advertise it correctly. Fixed by making the Resource Manager tab's checklist conditional: hidden (and `OPERATION_MODE_BASED_CONTROL` advertised automatically) when `Control type: OMBC`; shown, exactly as before, only when `Control type: None` - the only case where "advertised" and "implemented" can genuinely differ, since the user is wiring their own control-type node(s) and the RM has no way to infer what those advertise. The OMBC checkbox option itself was dropped from that list entirely, since checking it while `Control type: None` would advertise a capability nothing in the node actually implements.

**Advertised power measurement follows the D-Bus config, not the Resource Manager tab, when Transport: D-Bus.** Same class of bug as the Control Types one above, found the same way (real editor use, this time reported directly: a user set the Resource Manager tab's Power Meas. field, expecting it to control the D-Bus property/relay, and it silently did nothing - the D-Bus config's own, separate Power Meas. field is what actually mattered). Two independently-editable "Power Meas." pickers - one driving what's *advertised* (`ResourceManagerDetails.provides_power_measurement_types`), one driving what's actually *declared and relayed* on D-Bus - can drift out of sync exactly like the Control Types case, and did. Fixed the same way: when `Transport: D-Bus`, `rmDetails.providesPowerMeasurementTypes` is derived from the `s2-dbus-config` node's `measurementType` instead of the Resource Manager tab's field, and that field is hidden (with a hint pointing at the Connection tab) rather than left as a second, ignorable control. Required moving the `s2-dbus-config` lookup earlier in `s2-resource/index.ts` - it now happens before `rmDetails` is built, not inside the later `Transport: D-Bus` setup block, so both need it once instead of fetching (and risking drifting) twice.

**A "Default mode" dropdown on the Control Type tab replaces the need to manually wire an Inject node for the common "always start in this mode" case.** Found via real CEM testing: `control-type-ombc`'s existing "Pre-connection default status" requirement already lets a confirm message sent before any CEM connects seed the default `OMBC.Status` - but reaching it required wiring a separate Inject node into `s2-resource`'s input with a hand-typed mode UUID, which the user pushed back on ("I don't like that I'd have to add that inject node manually"). Fixed by adding a `defaultOperationModeId` config field, populated by a dropdown of the OMBC tab's own mode list (kept in sync as modes are added/removed/renamed, since mode ids are generated client-side and only exist once the editableList is built - there's no static option set to fall back on). At deploy time, `s2-resource` feeds this straight into `OMBCController.handleInput()` as a `confirmedOperationModeId` confirm with no `cemId`, immediately after constructing the controller - functionally identical to what the manually-wired Inject node already did, just built in. A later confirmation (from the CEM, or a manually-wired one) still overrides it normally, since `handleConfirm` always just overwrites whatever default/persisted status came before. Rejected: auto-selecting the first mode (or the "Standby/off" protected mode) as an implicit default without the user choosing it - S2's `OMBC.Status` claims to report an actual measured/known state, and guessing one the user didn't confirm would be reporting a fact the RM doesn't actually know.

**Auto-confirming instructed mode changes is opt-in on the shared `OMBCController` class, but on by default for `s2-resource`.** Found via the same real CEM testing as the Default-mode gap above, one step later in the same session: even with a default mode seeded, a CEM instructing a *transition* to a different mode still got no updated `OMBC.Status` - `handleInstruction` only ever relayed the instruction downstream as a `ModeInstruction` and waited for a `ModeConfirmation`, which nothing in the test flow sent. Asked the user whether to make this unconditional, an opt-in default-off toggle, or an opt-in default-on toggle (risk being a real-hardware flow that already confirms based on device state and would now get an extra, premature auto-confirmation racing its own); the user picked **opt-in, on by default**. Implemented as `OMBCController`'s new `autoConfirmInstructions` option (default `false` in the class itself, so `s2-ombc`/`s2-ombc-config` - unasked and already able to wire real confirmation logic - are unaffected) plus a new "Auto-confirm mode instructions" checkbox on `s2-resource`'s OMBC tab, defaulting to checked. When set, `handleInstruction` calls the same `confirmMode()` tail `handleConfirm` already used (extracted into a shared private method returning whether the CEM had OMBC selected), immediately after resolving the instruction and emitting it downstream - so the CEM's `OMBC.Status` request and the `ModeInstruction` sent to the flow both still happen exactly as before, just no longer gated on a confirmation nothing was configured to send.

**Raw S2 message tracing moved to the Debug sidebar; the "Auto-confirm" checkbox now names its actual S2 message.** Two related usability requests from the same message: (1) "Most users won't be able to easily check the console logging, while the debug pane is already known to them" - `s2-resource`'s existing `config.debug`-gated `-> `/`<- ` traces (both `Transport: WebSocket` and `Transport: D-Bus`) now go through the same `publishToDebugSidebar()` helper `2026-09-06-s2-dbus-transport`'s design.md introduces for `s2-dbus`/`s2-websocket`, so all three transports behave identically here - no separate mechanism for `s2-resource`. (2) "we need to make it more clear what type of message [Auto-confirm mode instructions] is about... end users are probably new to S2" - relabeled to "Auto-confirm mode-switch requests (OMBC.Instruction)", naming the literal `message_type` a user will now also see appear in the Debug sidebar once they enable it - the two changes reinforce each other (see something named `OMBC.Instruction` in the sidebar, recognize the same term on the checkbox that controls how it's handled).

**Debug-sidebar entries gained cemId and Connect/Disconnect visibility (see `2026-09-06-s2-dbus-transport`'s design.md for the shared mechanism).** `s2-resource` shares the same fix as `s2-dbus`/`s2-websocket`: topics now name the cemId, and Connect/Disconnect events publish their own sidebar entry - previously only `Message` traffic showed up, so a CEM connecting or disconnecting (or a message with no way to tell which CEM it was for) was invisible without checking the runtime log.

**`ModeInstruction`'s `power`/`rawMessage` fields renamed for S2 clarity - user-chosen shape.** Requested directly, twice: "isn't clear _which_ CEM" fed straight into the fix above; separately, "'power' is the expected power, but I expect a better S2 lingo there... 'rawMessage' should be something like rawS2Message". For `rawMessage` the user's own suggested name was used as-is. For `power`, the choice between a plain rename (`powerW`, same `[L1,L2,L3]` array) and an S2-shaped restructure (array of `{commodity_quantity, value}` pairs, matching S2's own PowerMeasurement/PowerRange values and this codebase's existing `PowerMeasurementValue` type) was a real fork with different downstream consequences (a flow reading `power[0]` as a number would need updating either way it's renamed, but the restructure also changes what each element *is*) - put to the user directly with both shapes previewed; they picked the S2-shaped restructure. Landed in `OMBCController` (`src/lib/s2/ombc-controller.ts`), shared with `s2-ombc` - not an `s2-resource`-specific change, but exercised through `s2-resource` in this session's testing. `calculatePower()` now returns `PowerMeasurementValue[]` directly instead of a plain tuple. The one real-world consumer found for the old shape, `examples/opportunity-loads-sg-ready-ombc.json`'s Function node, was updated (`powerValues[0]` was treated as a raw L1 watt number; now needs `.value`) - its `s2.payload.values` passthrough already worked unchanged, since `OMBCController.handleInput`'s `PowerMeasurement` case already accepted this exact `{commodity_quantity, value}[]` shape as one of its input forms.

**`s2-resource`'s node label no longer falls back to a default RM name.** Requested directly: "we now pre-fill the name with 'RM: Virtual'. The node-red way is not to have it given a default name." The editor's `rmName` default (`'RM: Virtual'`) fed both the RM Name form field (arguably fine, matching `s2-rm-config`'s own precedent of giving a *config* node's identity field a sensible default) and, via `label: function () { return this.name || this.rmName || 's2-resource' }`, the node's own *canvas label* - the latter is what actually violated convention, since an unnamed regular node should show its type name, not a value pulled from an unrelated sub-field. Fixed both symptoms together: `rmName`'s editor default is now `''` (its placeholder text, "e.g. Boiler RM", already covered the "here's an example" role Node-RED convention expects), and the label function dropped the `rmName` fallback entirely. The runtime's own `config.rmName || 'RM: Virtual'` fallback (in `src/nodes/s2-resource/index.ts`, feeding the real S2 `ResourceManagerDetails.name` field) is untouched - that's a protocol-correctness safety net, not a UI pre-fill, and a genuinely different concern. `s2-rm-config` (pre-existing, a config node where this pattern is closer to standard practice) was deliberately left alone - the user's complaint was clearly about something newly introduced by this change ("we *now* pre-fill"), not that older node.

**Status stays green after a CEM disconnects, instead of reverting to the RM's generic grey.** Reported as "I thought the ring would be green, but it is gray... most of the time it falls back to grey" - initially suspected as a Node-RED editor rendering artifact (a plausible read of a single screenshot), but the user's follow-up (a side-by-side comparison with a plain function node's status, "did see the green ring once correctly, but most of the time it falls back to grey") pointed at a real, reproducible behavior difference rather than a one-off redraw glitch, which prompted tracing the actual status-setting code paths rather than trusting the initial rendering-glitch theory. Root cause: `S2ResourceManager.updateStatus()` (shared with `s2-rm`) reports `{fill:'grey', shape:'ring', text:'waiting for CEM'}` whenever its session count is 0 - both at construction (no transport has done anything yet) and every time a CEM disconnects (the transport is fine, just idle). For `s2-rm` with an external transport, grey is the only honest answer either way, since the RM has no visibility into transport state. `s2-resource`'s built-in transports know more: D-Bus registration or the WebSocket connection succeeding is itself meaningful information the generic RM status can't see. Fixed by tracking a `transportReady` boolean in `s2-resource` (not in the shared `S2ResourceManager`, which stays transport-agnostic) and wrapping the `onStatus` callback passed to `rm` to upgrade that exact grey/text combination to green while the transport is confirmed up. D-Bus's `transportReady` is set on `open` and never cleared by CEM `disconnect` events (the registered service persists independent of any one session); WebSocket's is set on `open` and cleared on `close` (a real transport-level disconnect, correctly shown grey while reconnecting).

**OMBC tab's inapplicable per-phase fields are dimmed for a single-phase D-Bus device.** Requested directly, with a screenshot: wiring a D-Bus config to a single phase (`nrOfPhases: 1`, `phaseSetting: 2` = "Wired to L2") still left all three of the OMBC tab's L1/L2/L3 power fields fully editable, even though only L2 is ever actually reported. Implemented in the shared `resources/s2-ombc-editor.js` widget rather than as an `s2-resource`-only DOM hack, since dimming needs to target both the "L1"/"L3" label text and their inputs as one unit, and those labels were previously bare text nodes with nothing to attach a class to - `addModeItem` now wraps each phase in its own `.s2-ombc-mode-phase-l<n>` group, and a new `setActivePhase(listSel, activePhase)` export dims/disables whichever groups don't match. `s2-resource` is the only caller (re-reading its referenced `s2-dbus-config` node's live `nrOfPhases`/`phaseSetting` at several points - transport change, config selection change, tab switch, and every new mode row - so edits made in the D-Bus config's own sub-dialog are picked up without requiring the outer dialog to be reopened); `s2-ombc-config`/`s2-ombc` have no phase-wiring concept at all and never call it, so their own per-phase fields are unaffected. Disabling (not just dimming) the inputs also prevents saving a value for a phase that will never be used, which would otherwise sit in the saved `systemDescription` looking meaningful.

**Checkbox labels inside a `.form-row` were silently clipped to 120px - a CSS specificity collision, not a positioning bug.** Reported with a screenshot: the info icon overlapped the "Show raw S2 messages in debug sidebar" label text. First fix attempt (giving `.s2-checkbox-label` its own `position: relative` + padding, matching `.tooltip-icon`'s assumed anchor) didn't help - the user's follow-up screenshot, after confirming via a deliberately unmissable "lime border" debug marker that the edited stylesheet genuinely was being served (ruling out caching/stale-deployment before spending more effort on CSS theories), showed the label's actual rendered box ending mid-sentence. That pointed at the real cause: this checkbox's `<label>` sits inside a `<div class="form-row ...">`, and `.s2-form .form-row label`'s `width: 120px !important` - a selector matching on the `label` element type, giving it higher specificity - was winning over `.s2-checkbox-label`'s own `width: auto !important` (a class-only selector) the entire time, regardless of the first fix's `position: relative` addition. The label was rendering at a hard 120px; visible text overflowed past that clipped box, and the tooltip icon (correctly positioned relative to *that* box) landed wherever fell within the first 120px rather than at the end of the actual text. Fixed with the exact specificity-tie-break trick this same file already uses for `label.s2-section-label` just above it: add the `label` element type to the selector (`.s2-form label.s2-checkbox-label`) so it ties `.form-row label`'s specificity and wins on source order (it's defined later in the file). This also fixes the same latent clipping on every other `.s2-checkbox-label` in the codebase (`s2-rm-config`'s role/control-type checkboxes, this node's own Roles/Control-Types grids) - never visibly broken there only because 120px happens to be close to their 116px grid-cell width, not because they were unaffected.

One more round after that: the icon moved to "the far right edge of the whole row" instead of mid-sentence. `.s2-checkbox-label` used `display: flex` (block-level - stretches to fill its container's width) where `label.s2-ombc-mode-checkbox-label`, a near-identical pre-existing rule further down this same file, correctly uses `display: inline-flex` (shrink-to-fit). With the 120px clip gone, `flex`'s real block-level behavior took over and the label filled its whole row, so the icon's `right: 2px` landed at that row's far edge. Changed to `inline-flex` to match its sibling. Explicitly does not explain the separately-reported "edit panel is too wide" observation - a label's own flex-stretch behavior only affects how it fills its *own* row, not how wide that row or the dialog itself is; that remains open, most plausibly Node-RED's own per-node-type resizable/remembered tray width (confirmed such a mechanism exists in the editor core - a `red-ui-tray-resize-maximised` state) rather than anything in this stylesheet forcing it.

That guess turned out wrong, and the user's own DevTools work found the real cause. Two facts ruled out "remembered per-type tray width": a freshly-dropped `s2-resource` node opened narrow (538px), while an existing one with `Transport: D-Bus` selected stayed wide (958px, non-round - a computed value, not a literal number anywhere in this stylesheet) even after dragging the resize handle; and the parent of `.s2-form` measured the same width, meaning it wasn't content inside `.s2-form` being clipped-but-still-measured, it was the dialog itself opening wide. The distinguishing factor between the two dialogs: only the D-Bus-transport one renders the Connection tab's "Feed a power reading..." hint paragraph, which embeds a JSON snippet in a `<code>` tag. Node-RED's own editor CSS sets `code { white-space: nowrap }` globally - forcing that snippet onto one unbreakable line - and the tray appears to size itself on first open to fit the widest unbroken content it finds. Fixed with `.s2-form code { white-space: normal }`, so the snippet wraps normally as part of the sentence around it; scoped to `.s2-form` (this file's existing convention) so it doesn't touch the separate, non-resizable help panel's own `<code>` styling. Existing already-widened node instances may need one manual resize-handle drag to shrink back down after this fix ships, since Node-RED likely remembers the size it already auto-picked for that specific instance - new instances, and any existing one not yet manually touched, should size correctly from the next open.

That, in turn, wasn't the full story either - "Tried with a fresh node, but on re-opening after deploying, it is still wide again." The user's own suspicion pointed at the actual dominant cause: `#s2-resource-ombc-mode-list` (and `s2-ombc-config`'s equivalent) had an explicit `min-width: 480px` applied via `$(listSel).css(...)`. That element lives on the Control Type tab, `display:none` until opened - which happens as soon as anyone actually configures an OMBC mode, i.e. essentially every real use of this node. Once opened, the dialog grows to fit that 480px floor, and Node-RED then appears to remember/restore that grown width for that specific node instance on later opens, even when reopening back on the (narrower) Connection tab - explaining exactly "fresh node opens narrow, but is wide again after deploying" (deploying is what happens after configuring OMBC modes, i.e. after visiting the tab that grows it). Removed the `min-width` call from both files' editableList setup (kept `min-height`, unrelated - vertical sizing only). Not a regression risk: the per-phase L1/L2/L3 fields (`.s2-ombc-mode-value-wrap`, itself `white-space: nowrap`) already carry their own intrinsic minimum width from their content, and `.s2-ombc-mode-row`'s existing `flex-wrap: wrap` lets the rest of the row (mode label, "Minimum time" fields) wrap onto additional lines on a narrower dialog instead of demanding one. The `<code>` fix above is a separate, independently-real issue and stays - both were genuinely forcing width, just via different mechanisms.

Still not the full story - "Unfortunately it doesn't work still... Is there another (min-)width somewhere?" This time a full audit of every `width`/`min-width` in this stylesheet and every relevant HTML file's inline styles turned up nothing further, which turned out to be the right conclusion for the wrong reason: there genuinely was nothing else *in our own code*. The decisive evidence came from the user's own careful A/B DevTools testing - selecting the exact same element (`.s2-form` itself) both times, ruling out an earlier mismatched-element comparison. `Transport: WebSocket` (default) reopens at 538.258px; `Transport: dbus` or `external` reopens at 958.812px - identical, to the pixel, to measurements taken *before* the two content fixes above. Our content changes had measurably zero effect on that number, which means it was never being computed from our current content in the first place. The user's own DevTools inspection then spotted it directly: Node-RED writes an inline `min-width` straight onto `.red-ui-tray-body` (`style="min-width: 539.453px; ..."` visible in the Elements panel) - evidently derived once from some state key rather than recomputed fresh per open, though exhaustively searching Node-RED core's minified source did not turn up the exact originating calculation (diminishing returns past a point - not worth chasing further given the fix below doesn't depend on knowing it). The user's own suggestion: override it with our own `!important`. That's actually the correct fix, not merely a workaround - `!important` in an external stylesheet is the one case that beats a plain (non-`!important`) inline style, regardless of load order or whenever Node-RED (re-)applies its own value. `.red-ui-tray-body:has(.s2-form) { min-width: 0 !important }` neutralizes it, letting our own content's genuine, already-correct sizing (from the two fixes above) take over. `:has()` scopes it to only trays containing our own form - Node-RED 4.1.10 (confirmed running) fully supports it - so no other node type's dialog is affected.

That override "still doesn't work" either - and the most likely explanation isn't that the `!important`-beats-inline-style reasoning was wrong, it's that the selector never got a chance to apply it: `:has()` needs a fairly recent browser (Chrome 105+/2022, Firefox 121+/2023) and silently matches nothing at all on anything older - no console error, no visible sign, the rule just quietly never fires. Rather than pin down the exact browser/version in use, replaced it with a `:has()`-free equivalent that achieves the identical override guarantee: `oneditprepare` finds the tray body via a known-unique field in this form (`$('#node-input-transport').closest('.red-ui-tray-body')`) and adds a marker class, `s2-narrow-tray`; the stylesheet targets `.red-ui-tray-body.s2-narrow-tray { min-width: 0 !important }` instead of `:has(.s2-form)`. This does introduce a cleanup obligation `:has()` never had - since Node-RED appears to reuse the same physical tray-body element across different node types' dialogs, the class needs removing again once this dialog closes, or it would leak onto whatever opens next. Added to both `oneditsave` and a new `oneditcancel` so it's cleared on every way the dialog can close.

## Risks / Trade-offs

- [Extracting `s2-rm`'s logic could subtly change its behavior] → The `s2-rm-protocol` spec's existing requirements and `test/nodes/s2-rm.test.ts` are the regression check; the extraction itself is required to keep `s2-rm`'s test suite passing unchanged.
- [Shared client-side script load order] → `s2-resource`'s script tag calls the shared widget functions only from inside `oneditprepare`/`oneditsave`, which run long after all node scripts have loaded, so exact `<script>` tag order between the two `.html` files doesn't matter in practice; still worth an explicit smoke test (deploy both nodes in one flow) rather than relying on that alone.
- [Two-toggle port recomputation done wrong could silently disconnect existing wires on redeploy] → Only recompute when the resolved slot exposure actually changes from the node's last-deployed state, matching Node-RED's own guidance for dynamic-port nodes.
