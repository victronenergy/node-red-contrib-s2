## Context

See proposal.md - Why. This change was opened to track review feedback from `2026-09-04-ombc-mode-minimum-duration` (PR #36, philipptrenz): validate S2 payloads against the formal JSON schemas from [flexiblepower/s2-json](https://github.com/flexiblepower/s2-json) instead of relying on structural checks scattered across each config editor and the message path having no schema backing at all.

The complication driving most of this document, now resolved (see Decisions): `s2-json` publishes schemas at multiple git tags, not just `v1.0.0`. This repo's `s2-rm`/`s2-ombc`/`s2-pebc` nodes implement S2 `0.0.2-beta` (`src/lib/s2/messages.ts`, `supported_protocol_versions: ['0.0.2-beta']`), matching what Venus OS actually ships (`s2-python` v0.8.1). `s2-json` turns out to also have a `v0.0.2-beta` tag (published 2023-09-21) with a full schema set, and - per a direct diff against `v1.0.0` - the two are structurally identical for every message type this repo implements.

## Goals / Non-Goals

**Goals:**
- Establish what schema-version gap exists between `s2-json`'s available tags and the deployed protocol (`0.0.2-beta`), and pick a schema source before committing to an implementation.
- Once resolved, validate both config-save-time payloads (Advanced-mode `systemDescription`) and message-path payloads (`s2-rm` send/receive) against a schema that actually matches `0.0.2-beta`.

**Non-Goals:**
- Migrating this repo's nodes to S2 v1.0.0, or claiming `1.0.0` in `supported_protocol_versions` - that's a separate, much larger change (protocol version support is decided by what Venus OS ships, not by this repo alone, and requires verifying behavioral/session-level compatibility, not just JSON payload shape) and explicitly deferred to a future change. The schema-shape equivalence found below is not evidence of full protocol compatibility - it only covers the payloads this repo already sends/receives, not S2's session/handshake semantics or message types this repo doesn't implement (full FRBC/DDBC/PPBC support).
- Replacing the existing structural checks in `s2-ombc-config`/`s2-pebc-config` (`isFriendlyRepresentable` and friends) - those check friendly/Advanced round-trip shape, a different concern from S2-spec conformance, and stay as-is regardless of this change.

## Decisions

**Resolved: use `flexiblepower/s2-json`'s own `v0.0.2-beta` git tag as the schema source.** The version gap this document originally flagged as unresearched turned out to already have an exact answer: `s2-json` has published a `v0.0.2-beta` tag (present since 2023-09-21) with a complete schema set - `s2-json-schema/messages/*.schema.json` and `s2-json-schema/schemas/*.schema.json` at that tag - covering every message type this repo sends/receives (`ResourceManagerDetails`, `Handshake`/`HandshakeResponse`, `SelectControlType`, `OMBC.*`, `PEBC.*`, `PowerMeasurement`, `PowerForecast`, etc.).

Verification done: a full diff (`gh api repos/flexiblepower/s2-json/compare/v0.0.2-beta...v1.0.0`) shows 86 changed files, but nearly all of it is the repo's own directory restructure (`s2-json-schema/messages/*` moved to `messages/*` at v1.0.0) plus each file's `$id` URL bumping to reference the new tag - zero shape difference. Every `OMBC.*`/`PEBC.*`/`ControlType`/`SelectControlType`/`ResourceManagerDetails` schema file was checked individually: content is identical between the two tags except three enum schemas (`ControlType`, `PEBC.PowerEnvelopeConsequenceType`, `PEBC.PowerEnvelopeLimitType`) gained an explicit `"type": "string"` in v1.0.0 - a minor hardening, not a behavior change for values this repo already sends. `ResourceManagerDetails.schema.json` (including its `maxItems: 5` on `available_control_types`, see below) is byte-identical in both, aside from the `$id` line.

Practical conclusion: for the message types this repo implements, `0.0.2-beta` and `v1.0.0` are the same schema. Pinning to the `v0.0.2-beta` tag specifically (rather than `v1.0.0`) is a self-documentation choice, not a functional necessity - it name-matches `supported_protocol_versions: ['0.0.2-beta']` in `src/lib/s2/messages.ts`, saving a future reader from re-deriving this equivalence. This schema-shape equivalence is *not* evidence that this repo could safely claim `1.0.0` in `supported_protocol_versions` - see the Non-Goals note above; that remains a separate, deferred decision.

Superseded: the original three candidate options (hand-fork from v1.0.0, wait for upstream to publish a beta schema, or validate only a version-stable subset) are no longer needed - a real `0.0.2-beta`-native schema source already exists upstream.

**Validator library and architecture:** `ajv` (+ `ajv-formats` for format checks like `date-time`), but as **devDependencies only**, not shipped to the device at runtime. `ajv` installs at ~2.3M - about 5x this project's entire other production dependency footprint combined (`dbus-native-victron` + `dbus-victron-virtual` + `ws` = ~440K) - which matters on the disk-constrained device this package ships to. `ajv-formats` compounds this: it lists `ajv` as a real (non-peer-only) dependency, so simply moving *our own* `ajv` reference to devDependencies doesn't help while `ajv-formats` stays a runtime dependency - it pulls the whole `ajv` package straight back in transitively.

Resolution: `scripts/generate-schema-validators.js` uses ajv's own standalone-code-generation feature (`ajv/dist/standalone`) to precompile every vendored message schema into a single checked-in file, `src/lib/s2/schema-validators.generated.js` (~450K plain JS, self-contained validator functions - regenerate by re-running the script whenever `src/lib/s2/s2-json-schema/` changes). The only runtime dependency the generated code has is `ajv-formats/dist/formats.js` for format checks - which is itself fully self-contained (no further `require()`s) - so the script also vendors that one file into `src/lib/s2/ajv-runtime/` and rewrites the generated code's `require()` path to point at it, and vendors any `ajv/dist/runtime/*` helper a given schema set might need the same way (none needed for the current vendored schemas). Net effect: zero npm packages installed at runtime for this feature (down from `ajv`+`ajv-formats` "npm install" pulling in 63 packages); ~460K shipped in `dist/` (the generated validators file + `ajv-runtime/formats.js`), replacing what would otherwise have been ~2.4M of `node_modules`. `src/lib/s2/schema-validation.ts` (still hand-written, unchanged in its own logic/API) just calls into the generated module instead of building a live `Ajv` instance.

**Known discrepancy, deliberately not blocking implementation:** `ResourceManagerDetails.schema.json` caps `available_control_types` at `maxItems: 5` (present in both tags, not a beta-only artifact). The human-readable S2 standard (docs.s2standard.org's `ResourceManagerDetails` page) states no such cap - it only describes the field as "The control types supported by this Resource Manager." Since `s2-rm-protocol`'s "`NOT_CONTROLABLE` is always advertised and cannot be disabled" requirement means every RM's `available_control_types` always includes `NOT_CONTROLABLE` in addition to its configured real control types, a resource configured with all 5 real control types (`OMBC`+`FRBC`+`DDBC`+`PPBC`+`PEBC`) would advertise 6 entries - exceeding this schema's cap despite being fully spec-compliant. This is suspected to be a defect in `s2-json`'s schema; upstream has been contacted to confirm (unresolved as of this writing). Decision: do not special-case or relax this constraint in the vendored schema for now - flag it (see the requirement in `specs/s2-message-validation/spec.md`) so outgoing `ResourceManagerDetails` is validated leniently on this one field rather than silently blocked from sending, and revisit once upstream responds.

**Second known discrepancy, same treatment: `provides_power_measurement_types` requires `minItems: 1`.** The S2 standard's own `ResourceManagerDetails` page marks this field "Mandatory" but gives no guidance on what value represents "provides no power measurement" (omit the field, empty array, or otherwise) - unlike `available_control_types` above, this one doesn't have independent corroboration (like `s2-cem-cli.py`'s own menu logic) pointing to a specific reading, but "mandatory" most naturally reads as "the field must be present," analogous to `provides_forecast: false` expressing "no forecast" via a mandatory boolean rather than omitting the field - not necessarily "must be non-empty." Decision: treat an empty array the same as the `maxItems: 5` case - advisory, not blocking - **and** separately default new `s2-rm-config`/`s2-resource` nodes toward actually providing power measurement (a checkbox on both editors' Power Meas. section, checked by default, gating the existing 3-phase-symmetric/per-phase type selector - see the requirement below), since we're still pre-`1.0.0` and can freely change this repo's own defaults to lean into what the standard appears to want, while still allowing a deliberate "no measurement" choice for real devices that need it.

## Risks / Trade-offs

- [The `maxItems: 5` discrepancy above causes outgoing `ResourceManagerDetails` to fail strict validation for a legal, already-shipped configuration] -> Mitigated by the requirement carving out this specific known field as non-blocking; revisit once `s2-json` upstream confirms whether it's a bug.
- [Schema-shape equivalence between `0.0.2-beta` and `v1.0.0` could be mistaken for full protocol compatibility] -> Explicitly called out as a Non-Goal above; `supported_protocol_versions` stays `['0.0.2-beta']` only, unchanged by this work.
- [`ajv`'s own upstream maintenance has slowed - last release/commit to `master` was 2026-04-24 (~5 months old as of this writing), with at least two open fix PRs unmerged since then] -> Accepted: `ajv` remains the de facto JSON Schema validator, and since it's now a devDependency only (generated code ships instead of the library itself), its own release cadence matters less than it would as a runtime dependency - a maintenance concern for keeping the generator script working during development, not for what actually ships. It did ship a real CVE fix (ReDoS via `$data` + `pattern`, CVE-2025-69873) as recently as Feb 2026, so security response capacity isn't gone. Revisit the generation approach if `ajv` itself becomes genuinely unmaintained.
- [A checked-in generated file (`schema-validators.generated.js`) can drift from the vendored schemas it was generated from if someone edits the schemas without re-running the generator] -> Mitigated by the file's own header comment naming the regeneration command, and by `VENDORED.md`/`ajv-runtime/VENDORED.md` both saying not to hand-edit the sources either. No automated staleness check exists yet - acceptable since the vendored schemas themselves are not expected to change except deliberately.
