## 1. Research: resolve the schema-version gap

- [x] 1.1 Diffed `s2-json`'s `v0.0.2-beta` tag against its `v1.0.0` tag (`gh api repos/flexiblepower/s2-json/compare/v0.0.2-beta...v1.0.0`) for every message/schema file this repo actually sends or receives (`ResourceManagerDetails`, `Handshake`/`HandshakeResponse`, `SelectControlType`, `OMBC.*`, `PEBC.*`, `PowerMeasurement`, `PowerForecast`). Result: structurally identical - the diff is a directory rename plus `$id` URL bumps, with only three enum schemas gaining an explicit `"type": "string"` in v1.0.0 (no behavior change for values already sent). See design.md's Decisions section.
- [x] 1.2 Found: `s2-json` already has a `v0.0.2-beta` tag (published 2023-09-21) with a complete, `0.0.2-beta`-native schema set - no forking or upstream request needed.
- [x] 1.3 Decision recorded in design.md: pin to `s2-json`'s `v0.0.2-beta` tag (self-documenting match to `supported_protocol_versions`), not `v1.0.0` - though the two are functionally equivalent for our purposes per 1.1. Explicitly NOT changing `supported_protocol_versions` to include `1.0.0` - schema-shape equivalence isn't evidence of full protocol/behavioral compatibility; that's deferred to a future change.
- [x] 1.4 Revisited `specs/s2-message-validation/spec.md`: existing requirements still hold as written. Added one new requirement carving out the known `available_control_types` `maxItems: 5` discrepancy (suspected upstream schema defect, unconfirmed - see design.md) as non-blocking, so it doesn't contradict `s2-rm-protocol`'s already-shipped "`NOT_CONTROLABLE` is always advertised" guarantee.

## 2. Implementation (unblocked - schema source resolved)

- [x] 2.1 Vendored `s2-json`'s `v0.0.2-beta` `messages/`/`schemas/` schema files into `src/lib/s2/s2-json-schema/` (with `VENDORED.md` provenance + upstream `LICENSE`). Added `ajv`/`ajv-formats` as **devDependencies only** (not shipped at runtime - disk-footprint constraint, see design.md): `scripts/generate-schema-validators.js` uses ajv's standalone-code-generation feature to precompile every vendored schema into a checked-in `src/lib/s2/schema-validators.generated.js`, vendoring the one runtime helper it needs (`ajv-formats/dist/formats.js`) into `src/lib/s2/ajv-runtime/`. `scripts/copy-schemas.js` copies only the generated validator file + `ajv-runtime/` into `dist/` (not the raw JSON schemas, which are build-time-only). `src/lib/s2/schema-validation.ts` (`validateS2Message()`) loads the generated validators, resolves by `message_type`, and treats the known `maxItems: 5` (`available_control_types`) and `minItems: 1` (`provides_power_measurement_types`) discrepancies as advisory per the spec delta. Unit tested in `test/lib/schema-validation.test.ts`. Verified via `npm ls --omit=dev --depth=0`: zero ajv-related packages in the production tree.
- [x] 2.1a Added a "Provides power measurement" checkbox (checked by default) to `s2-rm-config` and `s2-resource`'s Resource Manager tab, gating the existing 3-phase-symmetric/per-phase type selector - UI-only change (`src/nodes/s2-rm-config/index.html`, `src/nodes/s2-resource/index.html`); no backend wiring needed since the underlying `providesPowerMeasurement` field (consumed by `parsePowerMeasurementTypes()` in `s2-rm`/`s2-resource`'s `index.ts`) already treats an empty string the same as "no measurement". Verified live in a running Node-RED instance (default checked/type-selector-visible for a new WebSocket-transport node, unchecking hides the selector, round-trips on reopen; hidden entirely under Transport: D-Bus on `s2-resource`, where the D-Bus config's own Power Meas. field is already the single source of truth).
- [x] 2.2 Wire config-save-time validation into `s2-ombc-config`/`s2-pebc-config`'s Advanced-mode save path, with an actionable inline error on failure. `s2-ombc-config` already had this. `s2-pebc-config` had no Advanced/JSON mode at all at the time this task was written (only a Friendly `Grid Fuse`/`Custom` picker, forced to a symmetric range) - added one (`/s2/validate-pebc-constraints` endpoint in `src/nodes/s2-pebc-config/index.ts`, mirroring `s2-ombc-config`'s pattern; `parsePEBCPowerConstraintsInput()` in `src/lib/s2/messages.ts`; new `constraints` field on the config node, additive/backward-compatible - existing flows with only `gridConnection`/`customMaxPowerW` are unaffected), which also lets a user express an asymmetric import/export limit or a non-default commodity that Friendly mode still can't.
- [x] 2.3 Wire message-path validation into `s2-rm`'s session layer (`src/lib/s2/session.ts`) for both outgoing (`_send`) and incoming (`handleMessage`) messages, logging a diagnostic via `onError` on failure
- [x] 2.4 Added Jest coverage for the validation logic: `test/lib/schema-validation.test.ts` (valid/invalid/advisory cases across message types, malformed input, a full sweep of every `make*()` builder in `messages.ts`), plus `session.ts`/`resource-manager.ts`/`s2-rm`/`s2-resource` test fixtures updated repo-wide to be schema-valid now that real validation runs on every message path (turned up and fixed a couple of pre-existing test bugs along the way: an invalid `control_type` shorthand, a wrong `ReceptionStatus` field name, and a real product bug in `makePEBCPowerConstraints` sending `valid_until: null` instead of omitting it).

## 3. Verification

- [x] 3.1 Manual verification, live in a running Node-RED instance: `s2-ombc-config`'s Advanced mode was already covered by earlier verification. For the new `s2-pebc-config` Advanced mode - switching Friendly (`Grid Fuse: 3x25A`) to Advanced correctly converts to `{ commodityQuantity: 'ELECTRIC.POWER.3_PHASE_SYMMETRIC', minPower: -17250, maxPower: 17250 }`; editing to an invalid-JSON value disables Add/Update and shows the parse error; editing to a valid asymmetric range (`minPower: -3000, maxPower: 6000`) clears the error and re-enables Add/Update; switching back to Friendly with that asymmetric value is refused with an inline warning and stays in Advanced mode; saving and reopening the config node correctly re-derives Advanced mode from the persisted `constraints` JSON.
