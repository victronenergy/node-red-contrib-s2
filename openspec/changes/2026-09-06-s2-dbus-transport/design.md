## Context

See `proposal.md` - Why. `s2-rm-protocol`'s existing spec already defines the transport-agnostic message contract (`Connect`/`Message`/`Disconnect`/`KeepAlive` in, `s2Signal`/`S2/0/Active` out); `s2-websocket` is the reference implementation of that contract. `dbus-victron-virtual` (via `addVictronInterfaces()`'s `__enableS2`/`__s2Handlers`) already implements the S2-over-D-Bus session protocol itself (CEM-id tracking, keepalive timeout, Discover/Connect/Disconnect/Message/KeepAlive) as a standalone library - node-red-contrib-victron's own `s2-support.js` is just a thin wiring layer over it.

## Goals / Non-Goals

**Goals:**
- `s2-dbus` + `s2-dbus-config` reproduce `s2-websocket`'s message contract exactly, so `s2-rm` is transport-blind.
- No dependency, soft or hard, on node-red-contrib-victron.
- Lightweight power-measurement relay: accept measurement value(s) on the node's own input and answer `PowerMeasurementStart`/`Stop` with them, so a flow that already gets readings from the controlled load's own API doesn't need its own Start/Stop bookkeeping.

**Non-Goals:**
- The full `victron-virtual`-style minimal-meter D-Bus shape (energy counters, frequency, power factor, per-phase current/voltage, `NrOfPhases`/`Position`/`Connected`/etc.) - only the power-reading key(s) already tracked for S2 (`Ac/Power`, or per-phase) are exposed as real properties (see the reversed Decision below), not a general-purpose meter device.

## Decisions

- **Depend directly on `dbus-victron-virtual` + `dbus-native-victron`**, not on node-red-contrib-victron. Both are standalone, pure-JS, framework-agnostic packages already used this way by node-red-contrib-victron; `dbus-native-victron` has no native bindings, so there's no platform-specific install step. Alternative considered (soft-detect node-red-contrib-victron and call into it) rejected: this package has no soft or hard dependency on node-red-contrib-victron by design, so both can be installed independently. Confirmed with the user: node-red-contrib-victron does also have its own experimental S2 support built directly into its virtual acload/heatpump devices (`enable_s2support`, that repo's own `s2-support.js`) - a deliberate second, independent implementation for its own advanced use cases, not something this change should detect/reuse/replace. This repo's own `S2DbusTransport`/`s2-dbus`/`s2-resource` stay the natural choice for anyone not already running node-red-contrib-victron, or wanting the fuller S2 feature set (OMBC/PEBC control types, `s2-rm`'s full session handling) this repo provides.
- **D-Bus registration lives in a shared class, `S2DbusTransport` (`src/lib/transport/dbus.ts`), not directly in `s2-dbus/index.ts`** - added once `s2-resource` needed the same D-Bus registration as a built-in `Transport: D-Bus` option (see `2026-09-07-s2-resource-composite-node`). Mirrors `S2WebSocketTransport`'s existing shape exactly (an `EventEmitter` with `connect()`/`disconnect()`/`send()`, events `open`/`connect`/`disconnect`/`message`/`error`), so both `s2-dbus` and `s2-resource` construct one directly instead of duplicating D-Bus wiring. The one structural difference from the WebSocket class: `connect()` registers the service and waits for a CEM to call in, rather than dialing out - there is no reconnect-with-backoff loop, since `bus.requestName` either succeeds once or the node reports an error status.
- **Connection modes (auto/system/TCP) are reproduced conceptually, not imported from node-red-contrib-victron.** `s2-dbus-config`'s three modes match `config-client.js`'s pattern (session bus when `DBUS_SESSION_BUS_ADDRESS` is set for "auto", explicit system bus, or a TCP address via `dbus.createClient`) but are implemented directly in `S2DbusTransport.connect()` - there is still no dependency, soft or hard, on node-red-contrib-victron itself, only on the same `dbus-native-victron` primitives it also uses.
- **`deviceType` validation happens in `s2-dbus` (the node), not `s2-dbus-config`.** The config node only stores the value; `s2-dbus` checks it against a known-products list before calling `transport.connect()`, matching the spec's "fails to register... reports an error status" requirement - `s2-dbus-config` has no way to show a red status of its own since config nodes aren't deployed/wired independently.
- **D-Bus service name uses the node's own id (`nodeId`), not the S2 resourceId.** Found during real-device testing: the S2 resourceId is typically a UUID, and a service name built from it unsanitized (`virtual_s2_8f0a1c2e-3d4b-...`) is invalid - `requestName` never succeeds, so the service silently fails to register. Fixed two ways: (1) `S2DbusTransport` now takes `nodeId` instead of `resourceId` and sanitizes it (`[^A-Za-z0-9_]` → `_`) exactly like node-red-contrib-victron's `sanitizeIdForDbus`, and (2) switched to `nodeId` in the first place rather than just sanitizing the resourceId, since a Node-RED node id is already short and unique - a sanitized UUID is still needlessly long as a service-name suffix. This also let `s2-dbus` drop its `rmConfig` reference entirely (it existed only to read `resourceId` for this purpose) - `s2-dbus` now depends only on its own `s2-dbus-config`.
- **DeviceInstance is claimed via `addSettings()`/`com.victronenergy.settings`, not user-configured.** Reversed from the original "fixed/configurable field" plan (see Risks below, now resolved) once real-device testing raised it: `S2DbusTransport` calls `AddSettings` on `/Settings/Devices/virtual_s2_<nodeId>/ClassAndVrmInstance` (default `<deviceType>:100`) with the same retry-on-`ServiceUnavailable` backoff node-red-contrib-victron's `callAddSettingsWithRetry` uses, and parses the response the same way (`getDeviceInstance`'s two-shape fallback). `s2-dbus-config`'s `deviceInstance` field is gone - the instance is now persisted and stable across redeploys/restarts, and never collides with another device the way a user-picked fixed number could. Not carried over from node-red-contrib-victron: the legacy `ClassAndVrmInstance` migration logic (renaming old `generator`/`e-drive` class values) - irrelevant here, there's no pre-existing S2 D-Bus data to migrate.
- **Power measurement values ARE exposed as real D-Bus BusItem properties - reversed from this change's original plan.** Originally a pure input-value cache with nothing exposed on D-Bus (rejected the full `victron-virtual` minimal-meter shape as overkill - phase/position config and energy-meter semantics for a need most flows don't have). Requested explicitly after real-device use: the cached value(s) (`Ac/Power`, or `Ac/L{n}/Power` per the configured measurement type - the same keys, no more) are now declared as real properties on `S2DbusTransport`'s registered interface and pushed via `setValuesLocally()` on every update, independent of whether a CEM currently has S2 measurement active - so VRM/other Venus services can read the same value the CEM sees. The measurement-type vocabulary itself (`3_PHASE_SYMMETRIC` / `L1_L2_L3`) still matches node-red-contrib-victron's `s2-support.js`, now for real consistency of shape, not just naming. The cache/relay logic (deciding *when* to emit to the CEM) stays in `PowerMeasurementCache` (`src/lib/s2/power-measurement-cache.ts`, shared with `s2-resource`) as a node-level concern; only the D-Bus property *declaration* (which must be known at registration time - a D-Bus interface's property set can't change after export) lives in `S2DbusTransport` itself, taking a `measurementType` option for that reason.

- **`S2/0/Active` and `S2/0/Rm` are declared as ordinary BusItem properties on the registered interface, not left implicit.** Found via real-device testing: connecting a CEM to a deployed `s2-resource` and selecting a control type crashed the exchange with `org.freedesktop.DBus.Error.Failed ['Property S2/0/Active not found in properties.']`. Root cause: `dbus-victron-virtual`'s `__enableS2` support implements the S2 session protocol (Discover/Connect/Disconnect/Message/KeepAlive) but does NOT itself declare `S2/0/Active`/`S2/0/Rm` as properties - `addVictronInterfaces`'s `processPropertyChanges` throws `Property ${k} not found in properties.` for any key passed to `setValuesLocally()` that isn't in `declaration.properties`, and this class was calling `setValuesLocally({'S2/0/Active': ...})` (from `setActive()`) without ever declaring it. Fixed by declaring both (`S2/0/Active: { type: 'i' }`, `S2/0/Rm: { type: 's', ... }`, initial values `0`/`''`) exactly as node-red-contrib-victron's `s2-support.js` `TRANSPORT_PROPERTIES`/`TRANSPORT_DEFAULTS` already do, and wiring `__s2Handlers.Connect`/`Disconnect` to update `S2/0/Rm` (CEM identity) the same way. The thrown error surfaced to the CEM as a normal `org.freedesktop.DBus.Error.Failed` reply rather than an unhandled exception - consistent with `dbus-native`'s method dispatcher catching handler errors and converting them to an error reply, though this wasn't independently confirmed against the live process.

- **Raw S2 message tracing moved from `node.log()` to the Debug sidebar.** Requested directly: "Most users won't be able to easily check the console logging, while the debug pane is already known to them." Checked what the Debug sidebar actually is: the core Debug node (`@node-red/nodes/core/common/21-debug.js`) populates it by calling `RED.comms.publish('debug', {id, z, name, topic, msg}, false)` on the same editor-comms websocket every node's `RED` object already exposes - a documented part of the node-facing API, not something specific to Debug-node instances. A regular node can publish onto that same channel directly, which is exactly what `publishToDebugSidebar()` (`src/lib/node-red-debug-sidebar.ts`) does, tagging entries with this node's own `id`/`z`/`name` so clicking one in the sidebar highlights the right node - no Debug node needs to be wired in. Considered switching to `node.warn()` instead (the Debug sidebar already surfaces WARN/ERROR-level `node.log`-family calls automatically, via a separate `RED.log.addHandler` listener in the same core file) - rejected, since routine protocol traffic isn't a warning and would misuse the "yellow triangle" severity styling and Node-RED's warning counters. `msg` is sent as the parsed object (not the JSON string) so the sidebar's tree view can expand it, matching how a Debug node set to "complete msg object" renders a payload. Applied to `s2-dbus` and, for consistency (same UX gap, same fix), the already-shipped `s2-websocket` - both nodes' "Debug"/"Log raw S2 messages" checkbox is now "Show raw S2 messages in debug sidebar" / "Debug", gated identically. Lifecycle logging (connect/disconnect/service-registered, not gated by this checkbox) stays on `node.log()` - it's not "raw S2 message" traffic and is still useful in the runtime log/journal.

  Asked explicitly to check for other Debug-sidebar/Debug-node features worth using, not just the minimum needed to get messages showing up. Read the rest of the core Debug node/sidebar source (`@node-red/nodes/core/common/21-debug.js`/`.html`, `lib/debug/debug-utils.js`) end to end. Findings:
  - **Hover-to-highlight / click-to-reveal already work for free** with just `id`+`z` - the sidebar looks up `RED.nodes.node(o.id)` regardless of source type, so our directly-published entries behave exactly like a real Debug node's for canvas highlighting and node reveal.
  - **Added `path` (this node's `_flow.path`, when set) to `publishToDebugSidebar()`** - the one field the core Debug node always includes that this integration was missing, used for the sidebar's subflow breadcrumb and to reveal the correct instance when a node is nested inside a subflow. Cheap to add, matches core exactly, no behavior change for the (typical, non-subflow) case where it's `undefined`.
  - **The sidebar's "Selected nodes" filter can't specifically target/hide our messages** - that dialog only lists actual `type: "debug"` node instances (`requestDebugNodeList` filters on it explicitly), so `s2-dbus`/`s2-websocket`/`s2-resource` never appear in that checklist. Not a functional gap in practice: `filteredNodes` is a hide-list defaulting to empty, so an unlisted source stays visible under every filter mode ("All flows", "This tab only", and "Selected nodes" alike) - it just can't be individually toggled off there the way a real Debug node can (unchecking the whole "Show raw S2 messages" setting is the only way to turn ours off).
  - **The pop-out Debug window** (a separate browser window showing the same live feed, launched from the sidebar's own toolbar button) works with these messages automatically too - it's fed via the same `RED.comms` subscription the sidebar itself uses, nothing S2-specific needed.
  - **Per-message severity coloring exists** (`red-ui-debug-msg-level-<n>`, driven by an optional numeric `level` field, the same one `node.warn()`/`node.error()` calls carry when the runtime's own log-handler feeds them to the sidebar) - not used here, since routine protocol traffic isn't a warning/error, but it's an available lever if a future need arises to visually flag e.g. a rejected `ReceptionStatus` differently from routine traffic in the same view.
  - **No in-sidebar text search exists** in this Node-RED version, so nothing was missed there - only the "filter by flow/node" and pause/clear controls above.
- **`S2DbusTransport` always declares node-red-contrib-victron's full "minimal meter" D-Bus shape, not just the S2/measurement-specific properties.** Requested directly: "we need [to] expose all paths that we have on the node-red-contrib-victron virtual acload and heatpump devices here as well. Main reason is that the Victron UI expects all paths to be available." Read `node-red-contrib-victron`'s actual `src/nodes/victron-virtual/device-type/acload.js`/`heatpump.js` (both device-type modules are, in fact, identical in shape - a generic "minimal meter" with S2 support layered on via that repo's own `s2-support.js`) and its shared `device-type/shared/minimal-meter.js`, which builds the property set the wiki's grid/genset/acload/heatpump-meter page documents (Position, NrOfPhases, PhaseSetting, Connected, DeviceType, ErrorCode, IsGenericEnergyMeter, and per-phase Current/Energy-Forward/Energy-Reverse/Power/PowerFactor/Voltage, plus the top-level Ac/Energy-Forward/Reverse/Frequency/Power/PowerFactor aggregates). Reproduced that exact shape in a new `minimal-meter-properties.ts`, always merged into `S2DbusTransport`'s declaration/definition (both `acload` and `heatpump` are the only `KNOWN_DBUS_DEVICE_TYPES` this repo supports, so there's no device type where this shape wouldn't apply). "We should be able to set things as position and phase directly here" - implemented as new `nrOfPhases`/`position`/`phaseSetting` fields on `s2-dbus-config`, mirroring node-red-contrib-victron's own `acload_nrofphases`/`acload_position`/`acload_phasesetting` config fields exactly (including a single-phase device reporting under its configured line instead of always `L1`).
- **Values with no real data source are `null`, never fabricated - the "conservative" requirement.** Requested directly: "We should be conservative on setting actual values on the paths. Only when we know the value we should set it." Checked `dbus-victron-virtual`'s own `wrapValue()`: a property definition value of `null` is wrapped as `["ai", []]` on the wire - the library's own, already-supported convention for "declared but not yet known" (used elsewhere in that library, and implicitly relied on by node-red-contrib-victron's own `format: (v) => v != null ? ... : ''` pattern throughout `minimal-meter.js`). So every numeric path this transport has no live data for (Voltage, Current, PowerFactor, Frequency, Energy Forward/Reverse, and Power when no `measurementType` tracks it) is initialized to `null`, not `0` - genuinely more conservative than node-red-contrib-victron's own per-phase properties, which default to `0` unconditionally (their top-level aggregates are more careful, defaulting to nothing unless a `default_values` opt-in config is set - the same asymmetry this change avoids by using `null` uniformly). Paths this transport *does* know a value for at registration time - `Connected` (1, we're registering right now), `DeviceType`/`ErrorCode` (0, matching node-red-contrib-victron's own constants), `IsGenericEnergyMeter` (0, since this is always a "full" S2-capable device, never a plain meter), `NrOfPhases`/`Position`/`PhaseSetting` (from config), and the `measurementType`-tracked power key(s) (0, then kept live via `setMeasurementValues()`) - get a real value, not `null`. Deliberately out of scope: accepting input-fed values for the newly-declared Voltage/Current/PowerFactor/Frequency/Energy paths (only Position/Phase/NrOfPhases were asked for as directly settable) - a natural, small follow-up if a flow later has a real data source for one of them, matching the existing `measurementType`/`PowerMeasurementCache` pattern.

- **Debug-sidebar entries now include the real cemId, and Connect/Disconnect are visible there too.** Two gaps found using the sidebar-based logging from the Decision above for real testing: (1) every entry said "to/from CEM" with no cemId, useless once more than one CEM is in play - fixed by appending the actual cemId to every topic. For the D-Bus transport's outbound direction specifically, `msg.cemId` on the way out is always the fixed internal placeholder the RM's session is keyed by (this codebase supports one CEM per node; the RM never sees the real D-Bus-supplied id) - so `s2-dbus`/`s2-resource` each track the real cemId from the transport's own `connect`/`disconnect` events in a small closure variable instead, giving a topic that actually reflects which physical CEM the message is going to. (2) A CEM connecting or disconnecting was invisible in the sidebar - only `Message` traffic published anything. Fixed by publishing a debug-sidebar entry (topic suffixed `(Connect)`/`(Disconnect)`) alongside the existing `node.log()`/status-update calls on those events, for `s2-dbus`, `s2-websocket`, and both of `s2-resource`'s built-in transports.

## Risks / Trade-offs

- **[Risk] GX firmware may split Node.js packages across `/usr/lib/node_modules` (firmware-shipped) and `/data/home/nodered/.node-red/node_modules` (palette-installed).** Adding `dbus-victron-virtual`/`dbus-native-victron` as a second hard dependent (alongside node-red-contrib-victron's own) does not necessarily dedupe to one installed copy the way plain npm hoisting would in a single flat tree - actual resolution behavior on a real GX unit is unverified. → Mitigation: verify against a real device (or ask the user to) before or during implementation; not a spec-level concern, but should inform version-range choices in `package.json`.
- **[Risk, resolved] `DeviceInstance` persistence.** Originally deferred (fixed/user-configured field), then implemented via `addSettings()` once real-device testing showed it mattered - see the Decisions entry above.
- **[Trade-off, resolved] Measurement values weren't visible outside S2.** Originally accepted as a trade-off (cached in-memory only); reversed once requested - see the Decisions entry above. The remaining trade-off is narrower: still not a full meter device (no energy counters, frequency, power factor, `NrOfPhases` etc.) - revisit only if someone asks for that too.
